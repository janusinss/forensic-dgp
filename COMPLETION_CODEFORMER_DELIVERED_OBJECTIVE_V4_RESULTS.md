## What V4 establishes and what it does not

The actual intended objective ran: exact app float256 hole-only RGB L1 with the
existing clean256 targets, microbatch division by4 once, no additive boundary
training term, no PNG rounding/STE, and all old boundary acceptance gates kept.
All256 FIT component/clipping receipts match that contract. FIT raw predictions
were not saved, so those numerical FIT loss/clipping values are source-and-receipt
checks, not an independent pixel replay. Saved evaluation losses are recomputed.
First/last training losses concern different cases and do not prove a trajectory.

Removing the boundary term and aligning delivery did not meet the requirements.
This does not prove no loss can work; it rejects this finite recipe. Do not append
epochs, rescue an earlier snapshot after terminal failure, weaken gates or repeat
V4 unchanged. R1 was not overwritten or made worse by the rejected experiment.

## Representation review before any new training

The pinned CodeFormer forward uses hard top-one code lookup and detached code/
encoder features. V3/V4 froze the predictor plus original generator/codebook and
trained fusion only. The selected codes therefore stayed fixed for identical
inputs. Pixel-loss changes could not train that frozen prediction route. This
is a source limitation, not proof it is the sole cause of every defect.

Official supplementary research confirms a distinct clean-VQGAN teacher route in
[CodeFormer training source](https://github.com/sczhou/CodeFormer/blob/master/basicsr/models/codeformer_model.py).
The [official release](https://github.com/sczhou/CodeFormer/releases/expanded_assets/v0.1.0)
lists a512-code VQGAN candidate. It was acquired separately with API provenance,
exact size/hash and retained license. The local pinned architecture remains the
authority for the current app; current upstream source is supplementary.

Passive independent CPU state comparisons reject direct substitution: although
all329 shared tensor shapes match, the teacher codebook differs, all164 encoder
tensors differ and163/164 generator tensors differ. Same cardinality is not
same code semantics. No integer teacher-code labels or prior were substituted.
[Independent compatibility](outputs/completion_codeformer_hq512_teacher_assets_v1/independent_passive_compatibility.json)
and [next representation review](outputs/completion_codeformer_hq512_teacher_assets_v1/INDEPENDENT_NEXT_REPRESENTATION_REVIEW.md)
retain that result. Byte differences alone do not prove no mapping could exist.

Next justified step is a bounded zero-optimizer same-inpainting-codebook diagnostic:
compare actual covered-input predictions with explicitly labeled clean-context
oracle codes, keeping masks/context/fusion controlled. This asks whether the
existing target representation can yield useful filled regions before spending
more training updates. Clean hidden information is oracle evidence only, never
an app method, identity recovery or native-CCTV result. No diagnostic packet is
ready and no new training/inference or VM operation is implied by the review.
